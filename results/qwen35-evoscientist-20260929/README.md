archives in this directory. Extract an archive before inspecting its
`result.json`, commands, metrics, and server logs or running the summary

## Completed eight-request measurements

All arms completed eight requests and generated the same 15,617 output tokens.
The throughput metric is vLLM's `output_throughput` (generated tokens divided
by benchmark duration). The runner uses `--custom-output-len -1` and
`--ignore-eos` so each request generates the trace's requested token count.
Each arm started a fresh server. The second pair
reversed the arm order to expose time-dependent variation. The tuned first
pair reuses the baseline from the default trial; the tuned BidKV arm was run
after the default BidKV arm, so these are not consecutive paired runs.

| Configuration and order | Baseline tok/s | BidKV tok/s | BidKV change | BidKV policy calls / selections / failures |
| --- | ---: | ---: | ---: | ---: |
| Default BidKV, baseline first | 27.211 | 24.454 | -10.13% | 1,134 / 227 / 0 |
| `BIDKV_UTILITY_PREEMPT_WEIGHT=5.0`, baseline first | 27.211 | 28.635 | +5.24% | 1,014 / 32 / 0 |
| Same setting, BidKV first | 31.960 | 29.161 | -8.76% | 1,014 / 32 / 0 |

The +5.24% result **does not establish an advantage**: the reversed-order
replication is negative. The baseline varied from 27.211 to 31.960 tok/s with
the same input. Across the two tuned comparisons, BidKV averaged
28.898 tok/s and baseline averaged 29.585 tok/s (-2.32%). All raw
`result.json`, `metrics.txt`, server and benchmark logs,
commands and NPU snapshots are preserved in the two extracted run directories.
The original compressed snapshot is `core-results.tar.gz` (SHA-256
`ddc270e295d7f15935139149cc430ba96924528a021d7dc82f52a9286997db97`).

An earlier summary incorrectly included the Prometheus counter creation-time
series in the first baseline's preemption count. The corrected count is 949;
`summary-before-metric-correction.json` is retained for audit. This did not
change throughput or output-token counts.

## Short four-request measurements

The short mixed input uses `--max-model-len 2048`, 256 MiB KV cache per NPU,
concurrency 4, request rate 4, and `BIDKV_UTILITY_PREEMPT_WEIGHT=5.0`. Each arm
completed 4/4 requests and generated the same 4,907 output tokens. These were
two consecutive pairs with alternating order.

| Run order | Baseline tok/s | BidKV tok/s | BidKV change | Preemptions baseline / BidKV | BidKV selections / failures |
| --- | ---: | ---: | ---: | ---: | ---: |
| Baseline then BidKV | 151.351 | 143.431 | -5.23% | 10 / 14 | 7 / 0 |
| BidKV then baseline | 151.001 | 144.119 | -4.56% | 10 / 14 | 7 / 0 |

BidKV was called 14 times in each run. This configuration is consistently
worse than baseline. The logs show active selection of requests that were
about 85–98% complete. The complete raw
results are in `bidkv-qwen35-shortmixed4-256m-2048-20260929/`, with a
compressed snapshot at `shortmixed4-256m-preempt5.tar.gz`.

Increasing the completion penalty from 0.5 to 10 while keeping the preemption
penalty at 5 reduced active selections from seven to three per run, but did
not improve throughput:

| Run order | Baseline tok/s | BidKV tok/s | BidKV change | Preemptions baseline / BidKV | BidKV selections / failures |
| --- | ---: | ---: | ---: | ---: | ---: |
| Baseline then BidKV | 153.580 | 141.650 | -7.77% | 10 / 15 | 3 / 0 |
| BidKV then baseline | 152.639 | 141.692 | -7.17% | 10 / 15 | 3 / 0 |

The raw results are in `bidkv-qwen35-shortmixed4-completion10-20260929/` and
`shortmixed4-256m-completion10.tar.gz`. The next trial reverses the four
requests into ascending output-length order, a scheduling pattern that
[previous BidKV evidence](../../docs/evidence/sage-mate-20260905-bounded-preemption-matrix.md)
found less harmful; it retains the preemption penalty
of 5 and default completion penalty of 0.5.

That ascending trial produced +0.80% and -1.96% in two alternating pairs.
Both candidate arms had 10 policy calls and **zero active selections**; the
baseline and candidate each had 10 preemptions. The positive run therefore
cannot be attributed to BidKV's victim selection. All four arms completed
4/4 requests and generated 4,907 tokens. Raw results are in
`bidkv-qwen35-shortascending4-256m-20260929/` and
`shortascending4-256m-preempt5.tar.gz`.

## High-concurrency KV-pressure result

The first 12 EvoScientist rows were run at concurrency 12, request rate 4,
4,096 maximum model length and 512 MiB KV cache per NPU. BidKV used
`BIDKV_UTILITY_PREEMPT_WEIGHT=5.0`. The four arms alternated order, each
completed 12/12 requests, and each generated the same 24,148 output tokens.
The cache was under pressure: baseline made 850 preemptions in each repeat.

| Run order | Baseline tok/s | BidKV tok/s | BidKV change | Preemptions baseline / BidKV | BidKV calls / selections / failures |
| --- | ---: | ---: | ---: | ---: | ---: |
| Baseline then BidKV | 35.370 | 41.422 | **+17.11%** | 850 / 786 | 786 / 10 / 0 |
| BidKV then baseline | 35.966 | 39.795 | **+10.65%** | 850 / 711 | 711 / 7 / 0 |

The mean of the two paired percentage changes is +13.88%. Both repeats show
active BidKV selections and lower preemption counts, so this is a measured
benefit in this tested cell rather than a zero-call difference. Two pairs do
not establish a confidence interval or generalize to other workloads. Every
arm's log records `FULL_AND_PIECEWISE` and completed decode FULL graph capture.
The second BidKV server emitted an `EngineDeadError` in its output handler
while shutting down **after** the benchmark result and metrics had been saved;
the benchmark itself completed and its policy failure counter was zero.

Raw commands, `result.json`, Prometheus metrics, server logs and NPU snapshots
are in `bidkv-qwen35-evoscientist-first12-c12-512m-20260929/`. The exact
compressed snapshot is `first12-c12-512m-preempt5.tar.gz` (SHA-256
`a9d3889bb195fa3be913b9201145c86ff17ffb702a0a8bcd51d6f8fcaa4a46e9`).

## Reproduction

From `/workspace/vllm-hust-bidkv`, after installing the repository into
`vllm-hust-dev`, use
`scripts/run_qwen35_kv_pressure.py`. For example, the tuned eight-request pair
can be run with:

```bash
conda run -n vllm-hust-dev python scripts/run_qwen35_kv_pressure.py \
  --model /workspace/models/Qwen3.5-35B-A3B \
  --devices 2,3,4,5 \
  --trace results/qwen35-evoscientist-20260929/evoscientist-workload-custom.jsonl \
  --output-dir /workspace/qwen35-evoscientist-preempt5-reproduction \
  --num-prompts 8 --max-concurrency 8 --request-rate 4 \
  --max-model-len 8192 --kv-cache-memory-bytes 268435456 \
  --candidate-config '{"utility_preempt_weight":5.0}' --repeats 2
```

The positive high-concurrency cell used:

```bash
conda run -n vllm-hust-dev python scripts/run_qwen35_kv_pressure.py \
  --model /workspace/models/Qwen3.5-35B-A3B \
  --devices 2,3,4,5 \
  --trace results/qwen35-evoscientist-20260929/evoscientist-first12.jsonl \
  --output-dir /workspace/qwen35-first12-c12-512m-reproduction \
  --num-prompts 12 --max-concurrency 12 --request-rate 4 \
  --max-model-len 4096 --kv-cache-memory-bytes 536870912 \
  --candidate-config '{"utility_preempt_weight":5.0}' --repeats 2
```

For the short four-request trial, change the trace to
`evoscientist-short-mixed-4.jsonl` in this directory and use
`--num-prompts 4 --max-concurrency 4 --max-model-len 2048` with the same
256 MiB KV setting. The follow-up also sets
`"utility_completion_weight":10.0` in `--candidate-config`.

The script checks model shards, saves exact commands and provenance, alternates
arm order, requires complete requests and identical output-token totals, and
verifies that the BidKV selector was called without policy failures. The
working vLLM-Ascend-HUST installation required a compiled native extension;
`ascend-build-compat.patch.gz` records the source compatibility changes used to
build it for this environment.

The 96 MiB KV-cache trial on the short input was stopped before it could yield
any complete comparison. In its first baseline arm the cache remained at 100%,
three of four requests waited, and generation fell to about 2 tok/s. That
configuration is excluded from throughput comparisons; its logs are retained
in `shortmixed4-96m-aborted.tar.gz`. A 256 MiB trial on the same short input
was then completed, as reported above.
